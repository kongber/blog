# 7. 系统运行与维护（次重点）

运行维护占生命周期约 60%～80%。

**四个时间指标**

| 指标 | 含义 | 算法 |
| --- | --- | --- |
| MTTR | 平均修复时间，含通知、诊断、修复、测试 | 修复总时间 / 维修次数 |
| MTBF | 两次故障之间的平均运行时间，含检测和修复 | 总运行时间 / 故障次数 |
| MTTF | 从开始到第一次故障的平均时间，不含检测修复 | 正常运行总时间 / 故障次数 |
| MTTA | 从告警到确认的平均时间 | 告警到确认的总时间 / 事件数 |

另有 MTTD：从故障发生到被发现。MTTR、MTTD 通常很小，选择题里常认为 **MTBF ≈ MTTF**。

故障管理五活动：监视、调查、排查、恢复、收尾。故障原因七类：计划内维护、应用、人为、系统软件、系统硬件、相关设备、灾难。

**维护四类（论文常考，靠「变化从哪来」区分）**

| 类型 | 触发 |
| --- | --- |
| 改正性 | 上线后修缺陷、性能缺陷、误用 |
| 适应性 | **外部环境**变了：操作系统、硬件、数据格式、业务规则环境 |
| 完善性 | **用户要更多或更好**：新功能、体验、性能调优、重构 |
| 预防性 | 为将来好改，用今天的方法重做昨天的系统 |

可维护性要在需求、设计（高内聚低耦合）、编码（注释与规范）、测试（文档）、维护（配置管理、文档同步）各阶段埋下。

**遗留系统四象限**（水平轴业务价值从低到高？原书：水平是业务，垂直是技术，沿箭头从低到高。按逆时针记口诀「该记陶吉」）

| 象限 | 技术 / 业务 | 策略 |
| --- | --- | --- |
| 一 | 高技术、高业务 | 改造：增强功能或改数据模型，系统本身还留着 |
| 二 | 高技术、低业务 | 集成：接进别的系统，它自己是信息孤岛 |
| 三 | 低技术、低业务 | 淘汰：重做。业务根本变了、文档和人都没了、重做更便宜 |
| 四 | 低技术、高业务 | 继承：新系统完全兼容旧的功能和数据模型，并行后再切 |

**三种转换**

| 策略 | 何时用 |
| --- | --- |
| 直接 | 新系统不复杂，或旧系统已经完全不能用。没有过渡 |
| 并行 | 系统大、处理复杂、数据重要。新旧一起跑一段时间 |
| 分段 | 直接 + 并行，分期分批。系统大、旧系统还稳、一次性切换风险高 |
