# 2. 需求工程（超级重点）

需求工程贯穿全生命周期。书上两大过程：**需求开发** + **需求管理**。

- 开发四阶段：获取 → 分析 → 编写 SRS（需求定义）→ 验证。口诀：获分归雁。
- 管理：定义基线、处理变更、需求跟踪。口诀：基因变更。
- 需求工程回答的是「做什么、做到什么程度算成功」，不是「怎么实现」。

## 2.1 需求获取（次重点）

方法：访谈、问卷、采样、情节串联板、联合需求计划 JRP、收集资料、获取文档、参加业务实践。口诀：访问踩窗帘，合收十文。

**采样公式（案例考过，必须会算）**：

样本大小 = α ×（可信度系数 / 可接受错误）²

- α 默认 0.25（总体最离散，p=0.5 时 p(1-p) 最大）。
- 若已知缺陷比例 p，则 α = p(1-p)，样本会变小。
- 90% 可信度系数约 1.65。例：0.25×(1.65/0.10)² ≈ 68，取 69 张订单。

## 2.2 需求分析（非重点）

主要方法：结构化分析 SA、面向对象分析 OOA、面向问题域 PDOA。前两个是重点。

## 2.3 结构化分析 SA（超级重点）

思想：自顶向下、逐层分解。

分析模型以**数据字典**为核心，外围三层：

- 数据模型：ER 图
- 功能模型：DFD
- 行为模型：状态转换图

**DFD 四种基本符号**

| 符号 | 图形 | 含义 |
| --- | --- | --- |
| 数据流 | 带名字的箭头 | 有名字、有方向的数据 |
| 加工 | 圆 | 对数据流做变换 |
| 数据存储 | 双横线 / 开口矩形 | 可访问的存储。外部实体要用它，必须经过加工 |
| 外部实体 | 方框 | 系统之外的源或宿 |

记号集：Gane-Sarson 与 Yourdon-Coad 画法不同，含义相同。扩充符号：与 `*`、或 `+`、异或 `⊕`，输入输出都可用。

层次：顶层图把整个系统画成一个加工；再逐层分解。

**平衡原则（案例找错必考）**

- 父子图平衡：数据流个数一致、方向一致。
- 子图内部：
  - 黑洞：有入无出
  - 奇迹：有出无入
  - 灰洞：输入产生不了声称的输出
  - 数据存储正常应有读有写；某一张子图上可以只有读或只有写

状态转换图已被 UML 状态图取代，知道初态（实心圆）、终态（圆圈套实心圆）、状态（圆角矩形）即可。

## 2.4 面向对象分析（超级重点）

三种模型（真题考过）：

| 模型 | 回答 | 常用图 |
| --- | --- | --- |
| 功能模型 / 用例模型 | 要做什么 | 用例图（有的资料也提 DFD） |
| 动态模型 | 何时、受何事件、做什么 | 状态图、顺序图 |
| 对象模型 / 分析模型 | 有哪些对象、属性和关系 | 类图。最基础 |

教材重点是用例模型 + 分析模型（类图）。

**用例图元素**：参与者、用例、通信关联。包含 / 扩展 / 泛化作用于用例之间。

参与者在系统之外，可以是人、外部系统、硬件（传感器、读卡器）、时钟。参与者之间可以有继承。

构建用例四步：识别参与者 → 合并需求得用例 → 细化描述 → 调整模型。前三步必需。

用例描述（系分案例可能问有哪些栏）：名称、简要说明、事件流、非功能需求、前后置条件、扩展点、优先级。

**用例三种关系（箭头方向死记）**

| 关系 | 构造型 | 箭头指向 | 含义 |
| --- | --- | --- | --- |
| 包含 | «include» | 指向被包含的抽象用例 | 抽出公共行为，基本用例执行时必然执行 |
| 扩展 | «extend» | 指向基本用例 | 可选、有条件的附加场景 |
| 泛化 | 空心三角实线 | 指向父用例 | 子用例继承父用例 |

记忆：include 指向「被抽出去的那个」；extend 指向「被扩展的基本用例」。

**类的六种关系，强弱：泛化 = 实现 > 组合 > 聚合 > 关联 > 依赖**

| 关系 | 要点 | 线型 |
| --- | --- | --- |
| 依赖 | 临时使用，B 变可能影响 A | 虚线箭头，指向被依赖方 |
| 关联 | 稳定结构联系，可有多重性 | 实线 |
| 聚合 | 整体-部分，部分可独立存在，可属于多个整体 | 空心菱形在整体端 |
| 组合 | 整体-部分，部分生命周期与整体相同，只能属于一个整体 | 实心菱形在整体端 |
| 泛化 | is-a，继承 | 空心三角实线，指向父类 |
| 实现 | 类实现接口 | 空心三角虚线，指向接口 |

聚合「好聚好散」；组合「同生共死」。UML 里聚合和组合都是关联的特例。包含和扩展是依赖的特例。

## 2.5 UML（重点）

结构：构造块、规则、公共机制。公共机制四要素：详述、修饰、通用划分、扩展机制（构造型、标记值、约束）。

**4+1 视图**（用例为中心，和后面架构 4+1 是同一套思想，软考里会出现多个「4+1」，别混场景）

| 视图 | 看什么 | 谁关心 |
| --- | --- | --- |
| 用例视图 | 外部如何使用系统 | 最终用户 |
| 逻辑视图 | 功能模块、类、包 | 分析人员、测试人员 |
| 进程视图 | 并发、同步、线程 | 系统集成人员 |
| 实现视图 | 代码、构件如何组织 | 程序员 |
| 部署视图 | 软件到硬件节点 | 系统工程师 |

UML 2.5 共 14 种图。记结构图，其余是行为图。

- 结构图：类、对象、包、组合结构、构件、部署、轮廓（Profile，取代旧的制品图）
- 行为图：用例、活动、状态机
- 交互图（也是行为图）：顺序、通信（协作）、时间、交互概览
- **用例图在 UML 2.x 中是行为图**

UML 四种基本关系：依赖、关联、泛化、实现。

顺序图：对象、生命线、激活（执行发生）、消息；UML 2 交互片段可表达选择、循环、并行。案例常考。

活动图：活动、对象流、分支、并发/同步、分区（泳道）。用于业务建模和用例内部行为。

**SysML**：UML 面向系统工程的扩展。新增模块定义图、需求图、参数图。用例图描述场景交互；需求图描述需求之间的关系。

## 2.6～2.8 定义、验证、管理

- 需求定义的产物是 **SRS**。方法有严格定义法和原型法。
- 需求验证 = 需求确认。评审（正式、征求意见）/ 检查（正式且严格、非作者详查）/ 走查（非正式、作者讲解）。
- 需求测试在没有可执行系统时只是基于文本的概念测试。
- 基线：已正式评审批准，只能走正式变更控制。
- 变更流程两种说法都对：申请→评估→通告→实施→验证确认→发布；或识别问题→分析描述→分析与成本→实现。
- 有风险的做法：用户参与不足、忽略用户分类、需求不断加、需求含糊、镀金特性、SRS 过简、估算不准。
- **双向跟踪**：正向 = SRS 的每条需求都能在后续成果里找到；反向 = 设计/代码/测试都能在 SRS 里找到出处。国标要求双向可追踪。
